# Measuring responsiveness

[← Documentation](README.md)

**Protocol v1 · define the procedure before collecting results.**

This is a controlled local exploration, not a field INP study or a promise of faster search. Keep responsiveness and completion separate.

## Reproduce

Run commands from the repository root. Commit source changes before collecting publishable evidence; the runner records the tested commit and whether the tree was dirty.

Use the pinned Node version, install dependencies and Chromium, then build:

```sh
npm ci
npx playwright install chromium
npm run build
npm run preview --workspace @turnlet/demo -- --host 127.0.0.1 --port 4176 --strictPort
```

In another terminal, with the browser allowed to stay in the foreground:

```sh
node scripts/measure-demo.mjs docs/experiments/my-run.json
```

The runner refuses to overwrite an existing result. Set `DEMO_URL` only to an equivalent production preview. Do not interact with the measurement browser while it runs. Keep the machine's load and power settings stable; disclose unknown background load.

For a protocol smoke test, append `--dry-run`: one trial per mode per scenario. Dry-run data is not eligible for reported medians.

Inspect and summarize a completed run with:

```sh
node scripts/summarize-experiment.mjs docs/experiments/my-run.json
```

The checker expects protocol v1's 30 attempted trials and a clean source revision. Keep unsuccessful attempts in the record; it reports usable counts separately.

## Fixed scenarios

All trials use seed **42**, a **5 ms** Turnlet budget, and the same final query, `ceramix`.

| Scenario        | Products | Input                                                | Question                                                       |
| --------------- | -------: | ---------------------------------------------------- | -------------------------------------------------------------- |
| completed-large |   50,000 | Set the field to `cerami` without an event; type `x` | Same single completed search: responsiveness versus completion |
| rapid-large     |   50,000 | Type `ceramix` from empty, requesting zero delay     | What happens when later queries supersede earlier ones?        |
| completed-small |      500 | Set the field to `cerami` without an event; type `x` | What overhead appears on small work?                           |

Setting the prefix only prepares the field; it does not call search or dispatch an event. The measured character is a real browser-dispatched, trusted keyboard event generated by Playwright. No `dispatchEvent`, `fill`, or direct search-function calls substitute for measured interactions.

Rapid input is sequential automation, not simultaneous hardware input. Browser/driver backpressure can change the actual cadence between modes. Each input's arrival time and query are retained. Do not claim equal completed CPU work or an exact cancellation count from these trials.

## Order and environment

Run **five fresh-context, fresh-document trials per mode per scenario**, sequentially: blocking first in odd rounds, Turnlet first in even rounds. Do not discard slow trials. Retain failed trials and their errors; publish counts and missing samples.

Use headed Chromium at 1440 × 1000 with a **4× CDP CPU slowdown**, no network throttle, and localhost assets. This artificial slowdown is not a particular mobile device. Record commit, built-asset hash, dirty state, timestamp, browser version, OS/kernel, CPU, memory, Node version, and actual scheduler availability. Turnlet uses native `scheduler.yield` when available, otherwise timers. Do not generalize native-backend results to fallback behavior.

Catalogue generation finishes before input. Wait 500 ms after field setup; use a fresh context without workload warm-up. Comparisons include first-search/JIT effects. Rotate order to reduce, not eliminate, drift.

## Sampling

Wait for final results and a measured completion display, then wait **1000 ms** and read the DOM without clicking anything. Record:

- Current session INP candidate, state, target, and all three attribution components.
- Latest accepted search-completion time, as displayed to 0.1 ms.
- Final result IDs and status; equal seeded queries must agree.
- Trusted input timestamps and document visibility.

The demo's single [web-vitals subscription](https://github.com/GoogleChrome/web-vitals) reports live candidates with attribution. These are **live session candidates**, not finalized page-lifecycle INP or population percentiles. Input durations are browser-rounded; the 16 ms reporting threshold can leave no attributable sample. Preserve Waiting/Unavailable as `null`, never zero. Do not compute improvement ratios from missing readings.

Keyboard focus and scrolling are set programmatically before measurement. No save/reset/export interaction is included. The sample is taken before context closure; closure may finalize a different candidate, which this protocol does not capture. The input listener adds small instrumentation overhead in both modes. Video and tracing are off during measured trials.

## Reporting

For each mode/scenario, publish sample counts, median, minimum and maximum of available INP and completion readings. For five values, median is the third sorted value; for other counts, average the two middle values when needed. Missing/failed counts remain visible.

A percentage change, if used, must name its metric and use `(blocking median - Turnlet median) / blocking median × 100`. Do not merge scenarios, treat INP as completion, or present rapid-input differences as same-work acceleration.

Inspect result equality and input cadence before drawing conclusions. Keep a separate walkthrough video for orientation, not as timing evidence. Record package bytes from a fresh tarball independently; raw heap/GC costs are not established by this protocol.
